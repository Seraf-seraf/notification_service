# Тестовая стратегия Notification Service

Документ фиксирует тестовую стратегию до реализации. Тесты должны писаться до production-кода: сначала failing tests, затем минимальная реализация, затем расширение покрытия при появлении новых сценариев.

## Принципы

| Принцип               | Решение                                                                                                                                          |
|-----------------------|--------------------------------------------------------------------------------------------------------------------------------------------------|
| Test-first            | Для каждого публичного сценария сначала добавляется падающий тест, затем реализация.                                                             |
| Проверка всей цепочки | Интеграционные тесты покрывают путь от API/RabbitMQ message до PostgreSQL status history и вызова нужного provider adapter.                      |
| Идемпотентность       | Повторы API, RabbitMQ delivery и provider webhook проверяются отдельными тестами.                                                                |
| Надежность            | Temporary errors проверяются через retry/backoff, permanent errors - через немедленный `dropped`, превышение попыток - через DLQ/exhausted flow. |
| Наблюдаемость         | Request id, JSON logs и VictoriaMetrics метрики считаются частью контракта и покрываются тестами.                                                |

## Integration tests

| ID    | Цепочка                                     | Сценарий                                             | Что проверяем                                                                                            | Ожидаемый результат                                                                                                            |
|-------|---------------------------------------------|------------------------------------------------------|----------------------------------------------------------------------------------------------------------|--------------------------------------------------------------------------------------------------------------------------------|
| I-001 | API -> PostgreSQL                           | Создание batch                                       | Транзакционное создание `notification_batches`, `notifications`, начальной `notification_status_history` | Все записи созданы атомарно, notifications имеют `queued`.                                                                     |
| I-002 | API -> PostgreSQL -> Outbox                 | Создание outbox messages                             | Outbox запись на каждую notification                                                                     | Outbox содержит `notification_id`, `batch_id`, `channel`, `priority`, `attempt=1`, `request_id`.                               |
| I-003 | Outbox -> RabbitMQ                          | Публикация заданий                                   | Persistent messages и publisher confirms                                                                 | Сообщения опубликованы в durable queue, outbox помечен published только после confirm.                                         |
| I-004 | RabbitMQ priority                           | Priority `3` обгоняет `1` и `2`                      | Strict priority `1..3`                                                                                   | При доступности сообщений worker получает priority `3` раньше низких приоритетов.                                              |
| I-005 | RabbitMQ -> Worker -> SMS provider          | SMS notification                                     | Выбор SMS adapter и provider call                                                                        | Вызван SMS provider, сохранен `provider_message_id`, статус `queued -> sent`, message ack после commit.                        |
| I-006 | RabbitMQ -> Worker -> Email provider        | Email notification                                   | Выбор Email adapter и provider call                                                                      | Вызван Email provider, сохранен `provider_message_id`, статус `queued -> sent`, message ack после commit.                      |
| I-007 | RabbitMQ redelivery -> Worker               | Повторная доставка того же message после `sent`      | Идемпотентность worker                                                                                   | Provider не вызывается повторно, message ack, статус не меняется.                                                              |
| I-008 | Worker -> Provider temporary error -> Retry | Provider вернул `429/500/503` или `temporary_failed` | Retry flow                                                                                               | Notification остается `queued`, attempt увеличивается, message уходит в retry queue с backoff.                                 |
| I-009 | Retry -> Send queue                         | TTL retry истек                                      | DLX routing обратно в send queue                                                                         | Message возвращается в send queue с увеличенным attempt.                                                                       |
| I-010 | Retry exhausted -> DLQ                      | Превышен лимит attempts                              | DLQ/exhausted behavior                                                                                   | Notification становится `dropped`, пишется history, техническое сообщение попадает в DLQ или фиксируется как exhausted.        |
| I-011 | Provider permanent error                    | `invalid_recipient` или `permanent_failed`           | Постоянная ошибка доставки                                                                               | Notification сразу `dropped`, retry не создается.                                                                              |
| I-012 | Provider webhook -> PostgreSQL              | `delivered` после `sent`                             | Финальный статус доставки                                                                                | Current status `delivered`, history содержит `queued`, `sent`, `delivered` в хронологическом порядке.                          |
| I-013 | Provider webhook anomaly                    | `dropped` после `delivered`                          | Запрет отката финального статуса                                                                         | Current status остается `delivered`, событие игнорируется или сохраняется как anomaly без смены статуса.                       |
| I-014 | API history -> PostgreSQL                   | История подписчика после нескольких batch            | Полнота истории                                                                                          | GET возвращает все уведомления подписчика с batch id, channel, message, priority, current status, timestamps и полной history. |
| I-015 | Request id propagation                      | API -> Outbox -> RabbitMQ -> Worker -> Provider      | Сквозной request id                                                                                      | Один request id присутствует в response, logs context, queue payload, provider headers и status updates.                       |
| I-016 | Metrics middleware                          | HTTP request metrics                                 | VictoriaMetrics HTTP метрики                                                                             | Экспортируются request count и latency buckets по route/method/status code.                                                    |
| I-017 | Worker metrics                              | Worker success/failure/retry/drop                    | Метрики воркеров                                                                                         | Экспортируются processed, failed, retried, dropped, provider latency, queue lag.                                               |
| I-018 | RabbitMQ unavailable                        | Outbox publisher не может опубликовать               | Надежность outbox                                                                                        | Outbox остается unpublished, API-принятые notifications не теряются, publisher повторяет позже.                                |
| I-019 | PostgreSQL transaction rollback             | Ошибка внутри создания batch                         | Атомарность                                                                                              | Не остается частично созданных batch/notifications/history/outbox.                                                             |
| I-020 | Parallel same idempotency key               | Два одновременных POST с одним key                   | Race condition защиты                                                                                    | Создается один batch, второй запрос получает тот же результат или ожидаемый conflict при другом payload.                       |

## Фактическое покрытие в репозитории

Текущее покрытие запускается контейнерной командой:

```bash
make test
```

`make test` использует `infra/docker-compose.yml` вместе с `infra/docker-compose.dev.yml`, чтобы тестовый контейнер видел актуальные `app`, `bootstrap`, `config`, `database`, `routes` и `tests` без длинных volume flags в `Makefile`.

Файлы тестов:

| Файл | Покрытие |
|------|----------|
| `tests/Feature/NotificationApiTest.php` | HTTP API, validation, idempotency, история подписчика, фильтры и cursor pagination. |
| `tests/Feature/NotificationSchemaTest.php` | PostgreSQL schema, уникальные ограничения idempotency/outbox/provider message. |
| `tests/Feature/Outbox/RabbitMqOutboxTest.php` | Outbox publish order по priority, persistent AMQP properties, retry publish backoff. |
| `tests/Feature/Worker/NotificationDeliveryWorkerTest.php` | Worker send flow, provider selection, idempotent redelivery, retry/DLQ, webhook monotonic updates. |
| `tests/Feature/ObservabilityTest.php` | Request id middleware, HTTP metrics, worker/provider/queue metrics. |
| `tests/Feature/E2E/NotificationE2ETest.php` | Сквозные сценарии API -> outbox -> worker -> provider fake -> webhook/history, failures и idempotency. |
| `apps/smsprovider/main_test.go` | Mock SMS provider: idempotency, async statuses, temporary/permanent failures, webhook. |
| `apps/emailprovider/main_test.go` | Mock Email provider: idempotency, async statuses, temporary/permanent failures. |
